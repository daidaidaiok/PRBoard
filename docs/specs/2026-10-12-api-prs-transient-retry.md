# 2026-10-12 /api/prs 瞬时 GitHub 抖动被放大成硬错误

## 问题

看板报 `加载失败：GitHub 暂时不可用，且没有可用的本地快照`（`/api/prs` 502）。根因是两处缺陷叠加：

1. **服务端只试一次**：`listOpenPullRequests`（换 installation token + GraphQL）无任何重试，
   一次连接重置/快速 5xx 就失败。有快照时降级显示旧数据；**快照只在首次成功拉取后才写入**，
   所以首次加载/新用户遇抖动直接 502，无任何兜底。
2. **前端首败退避 180s**：`streak=1` 直接落 90s × 2¹，1 秒的抖动让错误横幅挂 3 分钟才自愈。

## 方案（选定）

- **服务端**：`fetchPullRequestsWithRetry`——快速失败隔 500ms 重试一次。预算边界：
  仅当「已耗时 + 500ms + 15s 单次超时（GITHUB_TIMEOUT_MS）」≤ 浏览器 20s 拉取预算
  （DEFAULT_FETCH_TIMEOUT_MS）才重试；慢失败（15s 超时已烧完预算）立即抛出走快照兜底。
  保证 `/api/prs` 永不超出客户端超时导致浏览器先放弃。
- **前端**：首败重试 5s（QUICK_RETRY_MS）起步，之后 10s/20s/40s… 指数翻倍至 720s 封顶。
  瞬时抖动秒级自愈；真宕机退避曲线依然生效。

### 候选与取舍

- 复用现成重试工具：仓库内无（`retry-policy.ts` 是 CI 结论重试、`workflow-retries.ts` 是 DB 表），
  引 p-retry 之类属过度设计 → **Build，内联**。
- 服务端按错误类型分类重试（只重试网络/5xx）：需要内省 Octokit 错误，收益有限
  （对硬错误多打一次调用无害且有界）→ 不做。
- 错误文案改造（可操作化）：1+2 落地后死端场景罕见且秒级自愈 → 范围外。

## 验收标准

- [x] 首次 GitHub 尝试快速失败时，服务端重试一次并返回新数据（不落快照路径）。
- [x] 慢失败（烧完客户端预算）不重试，直接走快照兜底，总时长不超 20s。
- [x] 前端首败后 5s 重试，后续指数退避至 720s 封顶。
- [x] 既有行为不回归：GitHub 持续失败仍走快照/502，退避封顶语义不变。
